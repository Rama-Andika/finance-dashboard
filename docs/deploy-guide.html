B. Deploy pertama untuk klien atau lingkungan baru

Dikerjakan sekali per klien dan lingkungan. Kerjakan berurutan dan centang yang sudah selesai (tersimpan di browser ini). Setelah selesai, deploy berikutnya cukup bagian A.

Bedanya bila ini deployment production (bukan staging)

Langkah B sama, dengan nilai berbeda. Ubah isian "Lingkungan" menjadi production dan "Port" (kebiasaan: staging 52xx, production 51xx) di atas, dan perintah mengikuti. Hal lain yang perlu diingat:

  • Mulai dari staging. Pasang di staging dulu, baru production, satu klien pada satu waktu. Bila ada masalah, --rollback klien itu dan hentikan.
  • Paket production harus dari tag stabil (vX.Y.Z) dan commit bersih.
  • CLIENT_ID production = nama klien (tanpa -staging), jadi awalan alamatnya /oxy-<klien>-finance-dashboard. init-env mengisinya otomatis.
  • Aturan file env production: APP_TODAY tidak boleh ada, dan LOG_LEVEL tidak boleh debug atau trace. env-check menolak file yang melanggarnya, dan aplikasi menolak start.
  • Database terpisah dari staging untuk klien yang sama. Bila sama, keduanya berbagi tabel dash_* dan membangun snapshot dua kali. Tidak ada pengaman yang mencegah file staging berisi alamat database production, jadi periksa DATABASE_URL dan nama perusahaan di sidebar.
  • Satu baris sudoers dan satu systemctl enable lagi untuk layanan production (nama layanannya berbeda dari staging). Unit systemd tidak perlu dibuat ulang.
  • Pasang saat sepi. Restart membuat aplikasi tidak menjawab beberapa detik sampai satu-dua menit.

    ExecStartPre=... env-check.mjsSebelum menyala, periksa file pengaturannya. Bila salah, layanan tidak naik dan log menyebut nama kunci yang salah.

    • open-package.mjs (hanya pada deploy pertama ini).
  2. Pasang tanpa mengaktifkan. Server, sebagai root 
    chown oxy:oxy /home/oxy/web-server/oxy-demo-staging-finance-dashboard-5205/open-package.mjs /home/oxy/web-server/oxy-demo-staging-finance-dashboard-5205/20261112070634-51480c1.tgz

    Paket dibuka dan dipasang (npm ci, mengunduh dependensi, bisa beberapa menit), tetapi tidak ada yang dijalankan. Hasil yang benar: PREPARED ... Nothing is switched. Di akhir ia mencetak perintah init-env.mjs create ...; langkah 8 memakainya.

  3. Siapkan akses database. Server, sebagai root

    Dashboard butuh tiga hal: nama database klien, user MySQL, dan kata sandinya. Sebaiknya buat user khusus yang hanya berhak atas satu database itu, bukan root. Kata sandi acak hanya huruf dan angka menghindari urusan karakter khusus. Jangan menempelkan kata sandi ke chat atau dokumen.

    Perintah membuat user MySQL khusus dashboard
    openssl rand -hex 16     # hasilnya dipakai sebagai KATA_SANDI; simpan sendiri

    Lalu masuk dengan mysql -u root -p dan jalankan (ganti NAMA_DATABASE dan KATA_SANDI):

    CREATE USER 'dashboard'@'localhost' IDENTIFIED BY 'KATA_SANDI';
CREATE USER 'dashboard'@'127.0.0.1' IDENTIFIED BY 'KATA_SANDI';
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX, DROP ON `NAMA_DATABASE`.* TO 'dashboard'@'localhost';
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX, DROP ON `NAMA_DATABASE`.* TO 'dashboard'@'127.0.0.1';
FLUSH PRIVILEGES;

    Dua alamat (localhost dan 127.0.0.1) karena MySQL kadang menganggap sambungan dari 127.0.0.1 sebagai localhost. Memakai root juga bisa (keputusan pemilik), tetapi root berhak atas semua database di server itu.

    Cukup tidaknya sisa koneksi MySQL

    Satu deployment membuka paling banyak 7 koneksi (5 untuk pengguna dan 2 untuk pembangunan snapshot di latar belakang), 14 bila staging dan production sama-sama jalan. Di mysql:

    SHOW VARIABLES LIKE 'max_connections';
SHOW STATUS LIKE 'Max_used_connections';

    Selisihnya (batas dikurangi puncak pemakaian) harus lebih besar dari 14. Bila tipis, turunkan DB_POOL_SIZE dan DASH_POOL_SIZE di file env.

    su - oxy -c 'node /home/oxy/web-server/oxy-demo-staging-finance-dashboard-5205/releases/20261112070634-51480c1/scripts/ops/init-env.mjs create --client demo --env staging --port 5205 --file /home/oxy/web-server/oxy-demo-staging-finance-dashboard-5205/finance-dashboard.env'
ls -l /home/oxy/web-server/oxy-demo-staging-finance-dashboard-5205/finance-dashboard.env

    Hasil yang benar: -rw------- dengan pemilik oxy oxy. SESSION_SECRET sudah diisi acak, dan DATABASE_URL sengaja kosong. Isi LOG_DIR dengan perintah ini:

    su - oxy -c "sed -i 's|^# LOG_DIR=.*|LOG_DIR=/home/oxy/web-server/oxy-demo-staging-finance-dashboard-5205/logs|' /home/oxy/web-server/oxy-demo-staging-finance-dashboard-5205/finance-dashboard.env"

  8. (Opsional) Buka untuk pengguna lain lewat domain.

    Langkah ini boleh dilewati bila hanya Anda yang memakai dashboard. Setelah langkah 11, dashboard hanya bisa dibuka dari server itu sendiri (Anda memakai terowongan SSH dari laptop). Kerjakan langkah ini bila orang lain (tim atau klien) harus membukanya dari komputer mereka lewat alamat web biasa, misalnya https://dashboard.contoh.com/oxy-demo-staging-finance-dashboard/. Caranya: pasang "penerus" (reverse proxy), yaitu program web di server yang menerima kunjungan di port 80/443 lalu meneruskannya ke dashboard. Isi kotak "Domain publik" di atas dulu.

    Satu domain cukup untuk banyak deployment (klien dan lingkungan berbeda): tiap deployment punya port dan awalan alamat sendiri, jadi menambah deployment tidak butuh DNS atau sertifikat baru, hanya satu blok di file HTTPS (langkah 7).

    Dengan httpd (Apache), teruji 2026-11-12 di CentOS 7

    Semua langkah memakai file baru dan tidak mengubah file lain. Bila di server sudah ada httpd di port 80 dan 443, pakai cara ini dan jangan memasang nginx. Setiap penerapan dijaga httpd -t: reload baru jalan bila Syntax OK, dan reload bersifat lembut (aplikasi lain tidak terputus). Untuk membatalkan, hapus file barunya lalu httpd -t && systemctl reload httpd.

    7a. DNS. Minta pemegang domain membuat catatan A: nama {DOMAIN}, nilai IP publik server (cek dengan curl -s ifconfig.me). Lalu periksa dari server (harus mencetak IP itu; bila kosong, DNS belum menyebar dan jangan lanjut):

    getent hosts dashboard.contoh.com

    Bila domainnya punya catatan wildcard (*) ke server lain, nama acak pun akan tampak "ada"; yang penting catatan untuk {DOMAIN} sendiri menunjuk ke server ini.

    7b. File port 80. Hanya mengenalkan nama ke httpd supaya sertifikat bisa dibuktikan. Belum ada yang diteruskan.

    cat > /etc/httpd/conf.d/dashboard.contoh.com.conf <<'EOF'
<VirtualHost *:80>
    ServerName dashboard.contoh.com
    ErrorLog /var/log/httpd/dashboard.contoh.com-error.log
    CustomLog /var/log/httpd/dashboard.contoh.com-access.log combined
</VirtualHost>
EOF
httpd -t && systemctl reload httpd

    Uji bahwa port 80 terjangkau lewat nama itu (harus mencetak ok; bila tidak, berhenti, karena sertifikat akan gagal dan Let's Encrypt membatasi percobaan yang gagal):

    mkdir -p /var/www/html/.well-known/acme-challenge
echo ok > /var/www/html/.well-known/acme-challenge/uji
curl -s http://dashboard.contoh.com/.well-known/acme-challenge/uji
rm -f /var/www/html/.well-known/acme-challenge/uji

    7c. Sertifikat HTTPS. certonly hanya mengambil sertifikat dan tidak mengubah konfigurasi httpd:

    certbot certonly --webroot -w /var/www/html -d dashboard.contoh.com

    Hasil yang benar: Successfully received certificate (berlaku 90 hari).

    7d. File HTTPS dan pengalihan dari HTTP. Sertifikat ditulis dengan cert.pem, chain.pem, dan SSLCertificateChainFile karena httpd 2.4.6 (CentOS 7) belum mendukung fullchain.pem di satu baris; di httpd 2.4.8 ke atas pakai fullchain.pem di SSLCertificateFile dan buang baris chain.

    cat > /etc/httpd/conf.d/dashboard.contoh.com-ssl.conf <<'EOF'
<IfModule mod_ssl.c>
<VirtualHost *:443>
    ServerName dashboard.contoh.com

    SSLEngine on
    SSLCertificateFile /etc/letsencrypt/live/dashboard.contoh.com/cert.pem
    SSLCertificateKeyFile /etc/letsencrypt/live/dashboard.contoh.com/privkey.pem
    SSLCertificateChainFile /etc/letsencrypt/live/dashboard.contoh.com/chain.pem
    Include /etc/letsencrypt/options-ssl-apache.conf

    ProxyPreserveHost On

    <Location "/oxy-demo-staging-finance-dashboard">
        RequestHeader unset X-Forwarded-For early
        RequestHeader set X-Forwarded-Proto "https"
    </Location>
    <Location "/oxy-demo-staging-finance-dashboard/health">
        Require all denied
    </Location>
    ProxyPass        /oxy-demo-staging-finance-dashboard http://127.0.0.1:5205/oxy-demo-staging-finance-dashboard timeout=180
    ProxyPassReverse /oxy-demo-staging-finance-dashboard http://127.0.0.1:5205/oxy-demo-staging-finance-dashboard

    ErrorLog /var/log/httpd/dashboard.contoh.com-ssl-error.log
    CustomLog /var/log/httpd/dashboard.contoh.com-ssl-access.log combined
</VirtualHost>
</IfModule>
EOF

    Lalu tulis ulang file port 80 supaya mengalihkan ke HTTPS (alamat verifikasi sertifikat dikecualikan supaya perpanjangan tetap jalan lewat HTTP), dan terapkan:

    cat > /etc/httpd/conf.d/dashboard.contoh.com.conf <<'EOF'
<VirtualHost *:80>
    ServerName dashboard.contoh.com
    ErrorLog /var/log/httpd/dashboard.contoh.com-error.log
    CustomLog /var/log/httpd/dashboard.contoh.com-access.log combined

    RedirectMatch permanent ^/(?!\.well-known/acme-challenge/)(.*)$ https://dashboard.contoh.com/$1
</VirtualHost>
EOF
httpd -t && systemctl reload httpd

    7e. Uji dari server. Hasil yang benar: httpd_can_network_connect --> on (bila off: setsebool -P httpd_can_network_connect 1), dashboard 200 atau 307, health 403 (memang ditutup dari luar), dan pengalihan login berupa path di bawah awalan dashboard (bukan http:// atau 127.0.0.1):

    getsebool httpd_can_network_connect
curl -sk --resolve dashboard.contoh.com:443:127.0.0.1 -o /dev/null -w "dashboard: %{http_code}\n" https://dashboard.contoh.com/oxy-demo-staging-finance-dashboard/
curl -sk --resolve dashboard.contoh.com:443:127.0.0.1 -o /dev/null -w "health: %{http_code}\n" https://dashboard.contoh.com/oxy-demo-staging-finance-dashboard/health
curl -skI --resolve dashboard.contoh.com:443:127.0.0.1 https://dashboard.contoh.com/oxy-demo-staging-finance-dashboard/ | grep -i "^location"
curl -sI http://dashboard.contoh.com/oxy-demo-staging-finance-dashboard/ | grep -iE "^(HTTP|location)"

    Lalu buka https://dashboard.contoh.com/oxy-demo-staging-finance-dashboard/ di browser dari komputer lain: gembok tanpa peringatan, login berhasil dan tetap login saat pindah halaman, nama perusahaan di sidebar benar.

    7f. Perpanjangan sertifikat otomatis. Sertifikat Let's Encrypt berlaku 90 hari. Karena memakai certonly, certbot tidak memuat ulang httpd sendiri, jadi pasang skrip pemuat ulang dan jadwal. Skrip ini aman untuk sertifikat lain (hanya satu reload lembut setelah tiap perpanjangan berhasil), dan --dry-run tidak menjalankannya, jadi ujilah langsung:

    mkdir -p /etc/letsencrypt/renewal-hooks/deploy
cat > /etc/letsencrypt/renewal-hooks/deploy/reload-httpd.sh <<'EOF'
#!/bin/sh
# Muat ulang httpd setelah sertifikat diperpanjang, hanya bila konfigurasinya valid.
/usr/sbin/httpd -t && systemctl reload httpd
EOF
chmod 755 /etc/letsencrypt/renewal-hooks/deploy/reload-httpd.sh
/etc/letsencrypt/renewal-hooks/deploy/reload-httpd.sh && echo "hook OK"

    Penjadwal (dua kali sehari; certbot baru memperbarui bila sisa masa berlaku kurang dari 30 hari). Hanya untuk sertifikat domain ini, supaya sertifikat lain tidak ikut tersentuh. Periksa dulu bahwa crond aktif:

    systemctl is-active crond
CB=$(command -v certbot)
cat > /etc/cron.d/certbot-dashboard.contoh.com <<EOF
SHELL=/bin/sh
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin
23 3,15 * * * root $CB renew --cert-name dashboard.contoh.com --quiet
EOF
cat /etc/cron.d/certbot-dashboard.contoh.com
certbot renew --dry-run --cert-name dashboard.contoh.com

    Hasil yang benar: active, baris jadwal dengan path certbot, dan all simulated renewals succeeded. Sertifikat yang sudah ada di server dengan cara perpanjangan lain (misalnya --apache) tidak ikut terjadwal oleh ini; periksa masa berlakunya dengan certbot certificates.

    7g. Menambah deployment lain di domain yang sama. Tidak butuh DNS, sertifikat, atau file baru. Pasang deployment barunya (bagian B, dengan klien, lingkungan, dan port baru), ubah isian di atas, lalu tambahkan satu blok ini di dalam <VirtualHost *:443> pada file {DOMAIN}-ssl.conf dan terapkan dengan httpd -t && systemctl reload httpd:

    <Location "/oxy-demo-staging-finance-dashboard">
    RequestHeader unset X-Forwarded-For early
    RequestHeader set X-Forwarded-Proto "https"
</Location>
<Location "/oxy-demo-staging-finance-dashboard/health">
    Require all denied
</Location>
ProxyPass        /oxy-demo-staging-finance-dashboard http://127.0.0.1:5205/oxy-demo-staging-finance-dashboard timeout=180
ProxyPassReverse /oxy-demo-staging-finance-dashboard http://127.0.0.1:5205/oxy-demo-staging-finance-dashboard

    Port tiap deployment harus unik di server (catat di satu tempat). Staging dan production klien yang sama sebaiknya memakai database berbeda, karena yang sama berarti berbagi tabel dash_* dan membangun snapshot dua kali.

    Dengan nginx (belum teruji di server nyata)

    Satu blok location per klien, proxy_pass tanpa garis miring di akhir, dan X-Forwarded-For diisi $remote_addr (menimpa, bukan menambah). Alamat /health ditutup dari luar. DNS dan sertifikat sama seperti 7a dan 7c.

    return 404;
}

D. Perawatan sehari-hari

Dipakai setelah dashboard berjalan: mengubah pengaturan, membaca log, memeriksa setelah server dihidupkan ulang, membersihkan, dan mencadangkan. Perintah server dijalankan sebagai root, seperti di bagian lain.

D1. Mengubah nilai di file env, lalu restart

Perubahan di file env tidak perlu paket baru, tetapi baru berlaku setelah layanan di-restart (systemd membaca file itu hanya saat menyalakan layanan; reload tidak cukup). Urutannya: ubah file, periksa, restart, cek.

  1. Ubah nilainya. Server, sebagai root

    Dengan WinSCP (buka finance-dashboard.env, ubah, simpan) atau vi. Setelah menyimpan, pastikan izin dan pemiliknya tidak berubah:

    ls -l /home/oxy/web-server/oxy-demo-staging-finance-dashboard-5205/finance-dashboard.env

    Harus -rw------- dengan pemilik oxy oxy. Bila berubah, kembalikan: chown oxy:oxy dan chmod 600 pada berkas itu.

    Jangan mengubah CLIENT_ID, PORT, atau APP_ENV: ketiganya harus sama dengan paket dan nama folder deploy, dan env-check akan menolaknya. Mengganti DATABASE_URL berarti membaca database lain tanpa pengaman apa pun, jadi setelahnya pastikan nama perusahaan di sidebar benar.

  2. Periksa file. Server, sebagai root 
    su - oxy -c 'node /home/oxy/web-server/oxy-demo-staging-finance-dashboard-5205/current/scripts/ops/env-check.mjs /home/oxy/web-server/oxy-demo-staging-finance-dashboard-5205/finance-dashboard.env'

    Hasil yang benar: env-check: OK (...). Pemeriksaan ini hanya menyebut nama kunci dan nomor baris, tidak pernah nilainya. Bila ada ERROR, perbaiki dulu: layanan yang di-restart dengan file salah tidak akan naik.

  3. Restart dan cek. Server, sebagai root 
    systemctl restart oxy-finance-dashboard@demo-staging-finance-dashboard-5205
curl -s http://127.0.0.1:5205/oxy-demo-staging-finance-dashboard/health

    Harus menjawab {"status":"ok",...}. Aplikasi tidak menjawab beberapa detik selama restart, dan tab browser yang terbuka perlu dimuat ulang, jadi sebaiknya saat sepi. Bila tidak sehat, lihat log (D2).

Mengganti rahasia sesi (SESSION_SECRET)

Jarang diperlukan (misalnya bila rahasia itu bocor). Setelah diganti dan di-restart, semua pengguna keluar dan harus login lagi. Perintah create milik init-env menolak menimpa file, jadi untuk ini ada perintah khusus yang hanya mengganti satu nilai:

su - oxy -c 'node /home/oxy/web-server/oxy-demo-staging-finance-dashboard-5205/current/scripts/ops/init-env.mjs rotate-secret --file /home/oxy/web-server/oxy-demo-staging-finance-dashboard-5205/finance-dashboard.env'

Lalu periksa dan restart seperti di atas.

D2. Membaca log aplikasi

Ada dua sumber. Log layanan (journalctl) memuat apa yang terjadi saat aplikasi menyala atau mati. Log aplikasi ada di folder logs/, satu berkas per hari: app.<tanggal>.<nomor>.log, memuat setiap permintaan, login, dan galat. Isinya tidak pernah memuat kata sandi, nilai parameter SQL, atau nama pengguna yang diketik.

Bila pengguna melaporkan galat di layar, mintalah kode di belakang tanda pagar (CODE#20261112-153451-wjgxs). Bagian setelah tanda pagar adalah ID permintaan; cari seluruh barisnya:

su - oxy -c 'node --env-file=/home/oxy/web-server/oxy-demo-staging-finance-dashboard-5205/finance-dashboard.env /home/oxy/web-server/oxy-demo-staging-finance-dashboard-5205/current/dist/ops/logs-find.mjs <id-permintaan>'

Pilihan lain untuk perintah yang sama (ganti <id-permintaan>): --level error (hanya galat), --since 14:00 --until 14:30 (rentang waktu), --user <id>, --path /summary, dan --help. Tanpa pilihan apa pun, ia menampilkan peringatan dan galat beberapa hari terakhir.

Tanpa alat pencari, lihat langsung:

ls -lh /home/oxy/web-server/oxy-demo-staging-finance-dashboard-5205/logs
tail -n 50 /home/oxy/web-server/oxy-demo-staging-finance-dashboard-5205/logs/app.*.log
journalctl -u oxy-finance-dashboard@demo-staging-finance-dashboard-5205 -n 100 --no-pager

D3. Setelah server dihidupkan ulang

Layanan sudah didaftarkan (systemctl enable), jadi seharusnya menyala sendiri. Periksa:

systemctl is-enabled oxy-finance-dashboard@demo-staging-finance-dashboard-5205 httpd crond
systemctl is-active oxy-finance-dashboard@demo-staging-finance-dashboard-5205 httpd crond
curl -s http://127.0.0.1:5205/oxy-demo-staging-finance-dashboard/health

Semuanya enabled dan active, dan /health menjawab ok ("db":"ok" berarti MySQL sudah menyala dan terjangkau). Bila httpd tidak ada di server Anda, abaikan barisnya. Bila dashboard menyala sebelum MySQL siap, /health sementara menjawab 503 lalu pulih sendiri setelah MySQL menyala; bila tidak pulih dalam beberapa menit, systemctl restart layanannya.

Belum teruji di server nyata: perilaku setelah server dihidupkan ulang.

D4. Membersihkan berkas paket lama

Pemasang membersihkan folder rilis di server sendiri (menyisakan 5 terbaru ditambah rilis aktif dan sebelumnya). Berkas .tgz yang Anda unggah tidak ikut dihapus dan menumpuk. Folder rilis berdiri sendiri, jadi paket yang sudah terpasang aman dihapus. Lihat dulu yang akan terhapus, lalu hapus; dua paket terbaru disisakan:

ls -1t /home/oxy/web-server/oxy-demo-staging-finance-dashboard-5205/*.tgz | tail -n +3
ls -1t /home/oxy/web-server/oxy-demo-staging-finance-dashboard-5205/*.tgz | tail -n +3 | xargs -r rm -f

Perintah pertama hanya menampilkan daftar; jalankan yang kedua bila daftarnya benar. Berkas open-package.mjs tidak ikut terhapus karena bukan .tgz.

D5. Mencadangkan yang tidak ada di paket

Kode aplikasi tidak perlu dicadangkan: setiap rilis adalah satu paket, dan paket baru selalu bisa dibuat dari repositori. Yang tidak ada di paket dan sulit dibuat ulang:

  • File env (finance-dashboard.env): memuat SESSION_SECRET dan alamat database.
  • Unit systemd dan aturan sudoers.
  • Konfigurasi httpd untuk domain Anda dan jadwal perpanjangan (cron).
  • Folder /etc/letsencrypt (sertifikat dan kuncinya; sertifikat juga bisa diterbitkan ulang).
  • Database adalah milik klien dan dicadangkan dengan prosedur mereka. Tabel dash_* hanya data turunan yang dibangun ulang otomatis, jadi tidak perlu dicadangkan terpisah.
tar -czf /root/cadangan-dashboard-$(date +%Y%m%d).tgz /home/oxy/web-server/oxy-demo-staging-finance-dashboard-5205/finance-dashboard.env /etc/systemd/system/oxy-finance-dashboard@.service /etc/sudoers.d/oxy-finance-dashboard /etc/httpd/conf.d/dashboard.contoh.com.conf /etc/httpd/conf.d/dashboard.contoh.com-ssl.conf /etc/cron.d/certbot-dashboard.contoh.com /etc/letsencrypt
chmod 600 /root/cadangan-dashboard-*.tgz
ls -lh /root/cadangan-dashboard-*.tgz
Berkas cadangan itu memuat rahasia (kata sandi database dan kunci sertifikat). Pindahkan ke tempat aman di luar server ini dan jangan diunggah ke tempat umum. Bila file yang disebut tidak ada di server Anda (misalnya tanpa httpd), tar menolak dan berhenti: hapus nama berkas itu dari perintah.
Catat sendiri, di luar repositori: daftar deployment di server ini (klien, lingkungan, port, domain, tanggal pasang). Aturan proyek melarang nama klien dan server ditulis di repositori, jadi panduan ini hanya memuat contoh.

Di server (setelah Anda mengunggah paket)

PerintahFungsi
node <folder deploy>/open-package.mjs <berkas>.tgzMembuka paket (nama rilis = nama berkas tanpa .tgz, jangan diganti) dan memasangnya. Tambah --prepare-only pada pemasangan pertama, --dry-run untuk melihat rencana. Aman diulang: rilis yang sudah terbuka lengkap tidak dibuka lagi.
node <folder deploy>/current/scripts/ops/install.mjs --statusDaftar rilis (mana current, mana previous) dan satu pertanyaan ke /health.
node <folder deploy>/current/scripts/ops/install.mjs --rollbackKembali ke rilis sebelumnya dengan tangan. Dua kali berarti maju lagi.
Aturan
  • Tag dan commit bersih. Paket hanya dibuat dari commit yang bertanda tag dan semua perubahannya sudah di-commit, supaya setiap rilis bisa dilacak ke satu versi dan satu commit.
  • Tag SemVer. Production hanya dari tag stabil (vX.Y.Z); staging dari tag stabil atau vX.Y.Z-rc.N; --local-only hanya untuk percobaan lokal (ditolak server). Panduan rilis: docs/release-runbook.md.
  • Tanpa jendela jam. Tidak ada aturan jam. Disarankan memasang di saat sepi: restart membuat aplikasi tidak menjawab beberapa detik sampai satu-dua menit, dan tab browser yang terbuka perlu dimuat ulang.
  • Paket cocok dengan folder. CLIENT_ID di paket harus sama dengan yang dikatakan nama folder deploy; paket staging tidak bisa masuk folder production.
  • Migrasi tambah-saja. Hanya tabel baru atau kolom baru yang boleh kosong. Jangan menghapus, mengganti nama, atau mengubah tipe kolom yang masih dibaca rilis sebelumnya.
  • Satu klien pada satu waktu. Mulai dari staging, lalu satu klien percobaan, pantau sampai hari kerja berikutnya, baru lanjut. Bila bermasalah: --rollback klien itu dan hentikan.
Sudah teruji di server nyata (2026-11-12, staging, CentOS 7): unggah dan pembukaan paket, --prepare-only, init-env, env-check, npm ci, 10 migrasi, sudo systemctl restart, pemeriksaan /health, login, dan akses lewat domain HTTPS dengan httpd. Belum teruji di server nyata: rollback (otomatis dan manual), pemasangan rilis kedua, production, penyegaran open-package.mjs oleh pemasang, penerus nginx, dan menyalakan ulang server. Kerjakan staging lebih dulu. Persiapan server baru (user, unit systemd, sudoers, penerus) ada di bagian B di atas.
