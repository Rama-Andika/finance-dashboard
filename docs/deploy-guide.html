Panduan alur deploy (semi manual)

Dari satu perintah di komputer pembangun sampai versi baru berjalan di server klien, termasuk apa yang terjadi bila gagal, dan fungsi setiap file untuk lingkungan, pembuatan paket, dan pemasangan.

1. Ringkasan dalam satu paragraf

Di komputer pembangun Anda mengetik npm run release:pack -- acme production. Skrip memeriksa bahwa commit bersih, membangun aplikasi khusus untuk klien itu, memeriksa hasilnya, dan membungkusnya menjadi satu berkas .tgz. Komputer pembangun tidak menyambung ke server. Anda mengunggah berkas itu sendiri, lalu menjalankan satu perintah di server, open-package.mjs: ia membuka paket (nama rilis diambil dari nama berkas, jadi tidak diketik) dan menjalankan pemasangnya, install.mjs. Pemasang itu memeriksa paket, memasang paketnya, memigrasi database, memindahkan pintasan current ke rilis baru, me-restart service, lalu menunggu alamat /health menjawab sehat dengan versi yang baru dipasang. Bila tidak sehat dalam 2 menit, pintasan dikembalikan ke rilis sebelumnya secara otomatis.

Dua hal yang tidak berubah: kode aplikasi tidak pernah membuka file env (laptop: scripts/local.mjs, server: systemd yang mengisinya), dan setiap rilis berdiri sendiri di folder sendiri, jadi berpindah rilis hanya memindahkan satu pintasan.

3. Urutan satu rilis

Langkah demi langkah, dengan kata sederhana

  1. Buat paket. npm run release:pack -- acme production. Commit harus bersih; versi diambil dari git describe (tag bila ada, selain itu kode commit). Aplikasi dibangun untuk CLIENT_ID klien itu, hasilnya diperiksa (versi, CLIENT_ID, semua paket yang di-import server ikut terpasang), lalu dikemas ke release-packages/. Di akhir, perintah mencetak langkah berikutnya.Komputer pembangun · gagal = tidak ada paket
  2. Unggah. Salin berkas .tgz ke server dengan cara apa saja (WinSCP, scp). Pada pemasangan pertama sebuah deployment, salin juga open-package.mjs (ada di sebelah paket) ke folder deploy.Anda
  3. Buka paket dan pasang. node <folder deploy>/open-package.mjs <berkas>.tgz. Skrip itu mengambil nama rilis dari nama berkas, membuka paket ke releases/<nama> lewat folder sementara (tidak pernah setengah terbuka), memeriksa isinya, lalu menjalankan pemasang. Setelah pemasangan berhasil, pemasang menyalin open-package.mjs dari rilis itu ke folder deploy, jadi salinan unggahan manual tidak pernah basi.Anda, di server
  4. Pemasang: periksa rilis. install.mjs membaca folder deploy dari letaknya sendiri dan menolak paket yang dibangun untuk klien atau lingkungan lain.Server
  5. Pemasang: siapkan. Mengambil kunci (mkdir .deploy.lock, hanya satu pemasangan sekali), release.mjs doctor, npm ci --omit=dev, env-check terhadap file env.Server · gagal = berhenti, folder rilis tetap ada, jalankan perintah yang sama lagi setelah diperbaiki
  6. Pemasang: migrasi database. dash-migrate.mjs membuat tabel dash_* baru bila ada.Server → database · gagal = berhenti, current tidak berubah
  7. Pemasang: ganti rilis. release.mjs activate: current menunjuk rilis baru, rilis lama menjadi previous. Pemindahan satu langkah (rename), tidak pernah setengah jadi.Server
  8. Pemasang: restart dan tunggu sehat. sudo -n systemctl restart, lalu health-check.mjs menanyakan /health sampai menjawab ok, dengan versi yang baru, terus-menerus 10 detik (paling lama 120 detik).Server
  9. Selesai atau kembali. Sehat: rilis lama dibersihkan (sisa 5 terbaru plus current dan previous), kunci dilepas. Tidak sehat: rollback ke previous, restart, cek lagi.Server

4. Hasil akhir dan kalau ada yang gagal

Tulisan terakhirArtinyaYang Anda lakukan
INSTALLED …Rilis baru sehat dan berjalan. Kode keluar 0.Tidak ada.
ROLLED BACK: …Rilis baru tidak sehat; rilis lama sudah berjalan lagi dan sehat. Pemasangan dianggap gagal (kode keluar 1).Cari sebabnya di log service (journalctl) atau logs-find.mjs, perbaiki, buat paket baru.
ACTION NEEDED: …Rilis baru tidak sehat dan rilis lama juga tidak menjawab, atau pintasan tidak bisa dikembalikan.Sekarang juga: journalctl di server, dan release.mjs list --root <folder>.
FAILED: …Berhenti sebelum current berubah (paket salah folder, file env hilang, npm ci, migrasi, kunci ada), atau rilis baru tidak sehat dan tidak ada rilis sebelumnya.Baca pesannya; kebanyakan menyebut perbaikannya sendiri. Perbaiki, lalu jalankan perintah install.mjs yang sama lagi.
PREPARED …Hanya untuk --prepare-only: rilis terpasang tetapi belum diaktifkan.Buat file env di server dengan perintah init-env yang dicetak.
Kunci tertinggal. Bila pemasangan terputus di tengah (koneksi SSH putus), folder <folder deploy>/.deploy.lock bisa tertinggal dan pemasangan berikutnya menolak. Pesannya memuat perintah untuk menghapusnya; pastikan dulu tidak ada pemasangan yang sedang berjalan.

Nama folder membawa tiga fakta: klien, lingkungan, dan port. Pemasang membacanya dari letaknya sendiri, dan env-check memastikan isi file env sama dengan nama folder. Paket dari komputer pembangun tidak membawa node_modules; server memasangnya sendiri (butuh akses ke registry npm). Berkas .tgz yang Anda unggah boleh ditaruh di mana saja di luar releases/. /home/oxy/web-server/ hanyalah contoh; folder induknya boleh berbeda, yang harus sesuai pola hanya nama folder deploy.

9. Aturan

  • Commit bersih. Paket hanya dibuat dari commit yang semua perubahannya sudah di-commit, supaya setiap rilis bisa dilacak ke satu commit. Staging boleh dengan --allow-dirty.
  • Tag tidak wajib. Versi = nama tag bila ada, selain itu kode commit. Sistem ini belum punya skema nomor versi resmi.
  • Tanpa jendela jam. Tidak ada aturan jam. Disarankan memasang di saat sepi: restart membuat aplikasi tidak menjawab beberapa detik sampai satu-dua menit, dan tab browser yang terbuka perlu dimuat ulang.
  • Paket cocok dengan folder. CLIENT_ID di paket harus sama dengan yang dikatakan nama folder deploy; paket staging tidak bisa masuk folder production.
  • Migrasi tambah-saja. Hanya tabel baru atau kolom baru yang boleh kosong. Jangan menghapus, mengganti nama, atau mengubah tipe kolom yang masih dibaca rilis sebelumnya.
  • Satu klien pada satu waktu. Mulai dari staging, lalu satu klien percobaan, pantau sampai hari kerja berikutnya, baru lanjut. Bila bermasalah: --rollback klien itu dan hentikan.
Belum teruji di server nyata: unggah dan pembukaan paket, sudo systemctl, nginx, npm ci di server, dan migrasi sungguhan. Alur pemasang sudah dites dengan tiruan, dan alatnya dengan program asli di folder sementara. Kerjakan staging lebih dulu. Persiapan server baru (sudoers, unit systemd, nginx) ada di docs/project-guide.md bab 10.9.3.
